## foremankit – delegation rules
- Delegate by default; write yourself only what needs your own context. Anything that would be > ~50 lines or spans several files (tests, scripts, benchmark and report code, documentation, summaries and tables of results) goes to foremankit: `delegator` subagent, MCP `delegate` directly, or `foremankit delegate ...` from Bash. Before writing a large file ask "is this bulk_code / data_script / summarize?" - if yes, delegate first and review the result. Integration, debugging on live systems and decisions stay with you. Small edits that need your context: do them yourself. Small MECHANICAL fixes in existing code (rename a variable, add a docstring, split one function, fix the issues listed by `foremankit check`/a linter, update callers after a signature change) go to a Haiku subagent (`Agent` with `model: haiku`, a self-contained prompt with absolute paths, the exact check command and "small Edit-tool edits, no rewrite"): the weekly limit is finite and Haiku is enough. Several such fixes in different files = several Haiku agents in parallel. Review the diff and run the tests afterwards.
- The user's weekly Claude limit is finite and every turn re-reads the whole conversation. Keep replies short and avoid polling loops (one background wait instead). Final reports are terse: at most ~8 lines or a short table - what is done, what is pending, the one decision needed; no recap of steps the user saw, no per-helper essays (helper list = one line or a compact table with cost); details live in the repo log, not in chat. When a conversation has become long (many tool results, a few hours or several dozen turns) and a natural breakpoint arrives (a task finished and committed, results delivered, a long background job started), say so in ONE line and suggest continuing in a NEW session after saving the state (what is done, where the files are, what is pending) to memory or the repo. Mention it at most once per breakpoint and never in the middle of a task.
- Pick `kind`: bulk_code, data_script, hard_code, long_context, quick, summarize.
- Size the task for the helper: ONE file or part per call, answer under ~4000 tokens (`max_output_tokens` close to the real need; the router warns above 8000 and lowers reasoning above 6000). Split bigger jobs. Free models cut off or lose track on whole-file rewrites; a task that needs the API you just changed stays with you (write it yourself or give a model the exact new signatures as `context_files`).
- Code standard (same in every session and tool): clean code after R. Martin, readable by a beginner - names that reveal intent, functions <= 20 code lines (comments and docstrings do not count) / 4 parameters / 3 nesting levels, no duplication or magic values, specific exceptions (never bare `except`), logic apart from I/O, a docstring on every module, class and public function, comments that explain WHY (units, formulas, workarounds) and, in numerical or domain code, teach the reader the model, the formula and the data structure, every file starts with a 2-4 line header saying what it does and why (module docstring in Python, `//` block in TS/C++), teaching comments are written together with the code and never added later by a model that sees one function (review them with whole-file context), tests named as sentences, no commented-out code. The full text is foremankit's `config/conventions.md`; kinds `bulk_code`, `data_script` and `hard_code` receive it automatically, a project may override it in `.foremankit/conventions.md`. Check python files with `foremankit check <file>` (or `verify="foremankit check <file>"` to make a delegated file pass it). Do not reformat code you were not asked to touch.
- Prefer `verify` + `verify_target` for code that a command can check (e.g. `verify="python -m pytest tests/test_x.py -q"`, `verify_target="tests/test_x.py"`): the router runs the command, sends failures back to the SAME cheap model (2 rounds) and keeps the file only if it passes, so you do not debug delegated code by hand. Only prefixes from routing.yaml `verify.allowed_commands` run.
- Preliminary review: for code that goes into a repo (more than ~50 lines, or touching security, data or shared interfaces) add `review=true` to the delegation (after `verify`), and run `foremankit review --diff <paths>` on your own changes before presenting them. The reviewer is a DIFFERENT source: the own local LLM pool or a paid model, never a free cloud. Findings are advisory; only blockers whose quoted evidence really appears in the code go back to the author (one round, then the check runs again). Treat the rest as a checklist to verify, not as truth: cheap reviewers also err.
- Quality problem (wrong code from the default chain, rejected twice) -> retry with `escalate=true` (DeepSeek Pro). Do NOT escalate after `TaskTooLarge`, an empty answer or a cut-off answer: the task is too big, split it. After one failed PAID call, stop and diagnose before spending again.
- Cost: a paid call whose worst case is above `budget.per_call_usd` (0.10) is refused. Pass `allow_cost=true` only after the user agreed to the amount.
- Two failed attempts at the same problem, or an architecture decision -> ask the `opus-advisor` subagent.
- Results land in `.agent-out/<id>.md`. Read them selectively (Grep/offset), verify with tests, lint or spot checks – not line by line.
- Sensitivity: process data (plant tags, PI/SQL extracts, internal docs) = `"internal"` (paid no-train Gemini, else the local LLM; fails closed, never reaches free/training providers; DeepSeek only when this machine accepts it via FOREMANKIT_ALLOW_INTERNAL_TRAINING: its policy allows training on prompts and stores data in China, so never for credentials, personal data or trade secrets). Credentials, personal data, recipes/trade secrets = `"private"` (own local LLM only, fails closed).
- To `"normal"` (free/external) models send only schema + a few anonymised rows, never whole datasets or credentials.
- Use relative paths in `context_files` and in delegated tasks.
- Independent tasks: issue several `delegate` calls in the SAME message (they run in parallel) instead of one after another. The router spreads them across sources: the local LLM serves one request at a time, so a second concurrent call moves on to the next allowed source. For long jobs run `foremankit delegate ...` in the background and keep working.
- `internal` tries the local LLM first (free, private) but ONLY for small `quick`, `summarize`, `bulk_code`, `data_script` tasks (limits in routing.yaml `llm.kinds`): it is slower than the clouds (roughly 30-55 tok/s on the Legion, 15-20 on the Firefly; see benchmarks/LATENCY_RESULTS.md), so `hard_code`, `long_context`, big inputs and `escalate=true` go straight to the strongest allowed cloud model (paid Gemini, or DeepSeek where accepted). Keep `max_output_tokens` close to the real need. Start a local server ONLY through `llama/start-qwen3.6.cmd` (never call llama-server.exe directly): it reuses an identical running server, refuses a second different one (each holds ~25 GB of RAM; Windows even allows two on the same port with different bind addresses) and holds a machine-wide lock. `-List` shows what runs, `-Replace` swaps it, `-Force` is for a deliberate second server on another port. Check `-List` before asking another machine's session to start one.
- Parallel by default: whenever a job splits into independent units (files, packages, directories, test groups), run the units in parallel: several `delegate` calls in one message, or several background processes of a batch script (one worker per package/directory). Serialize only what shares state (the same file, a shared build directory, tests that import code another unit is changing) and say which and why. A batch tool or script you write must be built for that layout (a worker per package, not one sequential loop over everything). Before starting a long job state in one line what runs in parallel and what must wait.
- Keep the user informed in the chat: before a delegation write one short line (`→ calling foremankit: <kind>, <sensitivity>` and the expected helper; for parallel calls one line listing all of them), and when the result arrives one line from the result header (`← response from <provider/model> in <s>, <cost>`; mention fallbacks and failures honestly). In the final summary list every helper used with its role, tokens and cost (`foremankit stats --days 1`), and say which ones were useful and which were wasted.
- `router_status` shows remaining free quota and paid spend; paid providers stop hard at the configured USD budget.
- The foremankit MCP tools may be "deferred" (listed by name only): load their schemas first with ToolSearch (`select:mcp__foremankit__delegate,mcp__foremankit__router_status`), otherwise the call fails. A `delegator` subagent does not need this.
- At the start of a work session call `router_status` once: it probes DeepSeek (free GET /models, re-probed every 10 min). DeepSeek is preferred over paid Gemini whenever it is reachable; if it is blocked on the current network, just continue (it is skipped automatically). Never try to bypass a network block.
